# Backend

The backend includes the read-only BookOrbit client, encrypted configuration, scanning, a durable delivery outbox, and an early administrator interface. Administration and the runtime are disabled by default and are not yet production-ready.

The Phase-2 schema is managed exclusively by Alembic. From `backend/`, run `alembic upgrade head`; set `BOOKORBIT_NOTIFIER_DATABASE_URL` to select the target SQLite file. The shipped default is only a local development path. Never create tables from application code in production.

The scanner/delivery runtime remains disabled until `BOOKORBIT_NOTIFIER_RUNTIME_ENABLED=true`. Enabling it also requires `BOOKORBIT_NOTIFIER_ENCRYPTION_KEY` with a dedicated Fernet key supplied by the deployment secret store. Migrate the database first; startup deliberately does not create or migrate tables.

Run locally after installing the project dependencies:

```text
uvicorn app.main:app --app-dir backend --reload
```

`POST /api/v1/poc/*` endpoints are disabled unless `BOOKORBIT_NOTIFIER_POC_ENDPOINTS_ENABLED=true` is set. They are development diagnostics only and must never be exposed publicly because they accept transient credentials.

## Local administrator setup

First migrate the database. Enable the interface with `BOOKORBIT_NOTIFIER_ADMIN_ENABLED=true`, set `BOOKORBIT_NOTIFIER_ADMIN_ORIGIN` to the exact browser origin (for example `http://127.0.0.1:8000` for local use), and supply `BOOKORBIT_NOTIFIER_SETUP_TOKEN` as a separate, randomly generated secret of at least 32 characters. Generate one with `python -c "import secrets; print(secrets.token_urlsafe(32))"` and keep it out of logs, source control and shared configuration. Open `/admin`, enter the setup token and an administrator password of at least 12 characters, then sign in. Remove the setup token from the environment after setup and restart the service.

### Local Docker Desktop

The repository's Compose configuration listens only on `127.0.0.1:18765` and stores the database in a named Docker volume. Before starting it, create `data/docker.env` privately with a separate Fernet key in `BOOKORBIT_NOTIFIER_ENCRYPTION_KEY` and a random setup token in `BOOKORBIT_NOTIFIER_SETUP_TOKEN`. The ignored `data/` directory must not be committed or included in the build context. Back up the encryption key separately: losing it makes stored credentials unreadable. From the repository root, run `docker compose build`, `docker compose run --rm notifier alembic upgrade head`, and `docker compose up -d`; open `http://127.0.0.1:18765/admin`. After creating the administrator, remove the setup-token line from `data/docker.env` and recreate the container with `docker compose up -d --force-recreate`. Keep the encryption key unchanged. This is a local development deployment, not a production release.

Remote access requires an HTTPS origin; plain HTTP is accepted only for localhost or loopback addresses. HTTPS must be provided by the deployment or a trusted reverse proxy, and the configured origin must match the externally visible browser address. Do not enable the development POC routes on an exposed instance. The UI supports setup, login, delivery counts, adding and editing sources and webhooks, discovering libraries, routing and sender profiles. Removing sources and the remaining Phase 4 screens are not implemented. Adding or routing sources and destinations requires a dedicated `BOOKORBIT_NOTIFIER_ENCRYPTION_KEY` even if the scheduler is disabled; keep that key backed up separately from the database.

The administrator menu separates the overview, libraries, webhook presets, arrivals, delivery history and settings into views. The selected view is reflected in the URL fragment. Switching views or the interface language keeps unsaved management form inputs in the current page; language switching retains them only in browser memory. Reloading or using the separate refresh action can still discard unsaved edits.

A disabled webhook with no delivery records can be removed after confirmation. This removes its local library routes and sender profile, without modifying the Discord webhook. Webhooks with any delivery record cannot be removed yet, even after successful delivery, so queued work and delivery history remain intact. Server removal is not implemented.

Each library can configure the initial metadata delay and maximum wait from zero to 604,800 seconds (seven days); the maximum must be at least the initial delay. Settings apply to newly detected media, while events already waiting retain their deadlines. A title is required for early release, whereas optional metadata never delays it. Retries are scheduled no later than the deadline, but checks run during source scans and can occur later because of scan intervals or outages.

The operational log also reports when metadata checks release media, defer them, or encounter source errors. These are server-level aggregate events: one entry can represent multiple media, and a pass can have more than one outcome. Source error text and credentials are excluded.

The operational log records successful server enable/disable changes and library routing, delivery and metadata-setting saves using IDs only, without configuration values or credentials. It is best effort and is not a complete security audit: if log storage is unavailable, the requested change can still succeed.

The delivery history displays the next scheduled attempt for queued/retry states and the start time of an in-progress delivery. Scheduled timestamps indicate the earliest possible processing time rather than a guarantee of immediate delivery.

The delivery history can be filtered by server, library and status, and downloaded as a UTF-8 CSV using the same filters. It contains at most the 10,000 newest matching delivery records and omits credentials, connection URLs and error messages; potentially formula-like text is prefixed for safer spreadsheet use. This export is not a backup and does not include individual attempt history.

The overview lists each server's most recently recorded library-scan result and, while the runtime is active, its next scheduled scan when available. A library scan is a historical observation, not a live connectivity test or an aggregate assessment of every library; scheduled times can be delayed by ongoing work and are reset when the process restarts.

The overview also shows up to five recently detected arrivals with covers loaded lazily through the authenticated administrator cover endpoint. The silent initial baseline is excluded, and a missing cover does not prevent the item from being shown.

Import Logs also includes a paginated library-scan history with server, library, result and UTC date filters. It displays scan times and counts but deliberately excludes stored error messages and connection details. This database history is separate from the rotated operational-event log.

Settings includes an optional operational-event viewer. Set `BOOKORBIT_NOTIFIER_LOG_DIRECTORY` to a writable directory to enable it (the local Compose deployment uses `/data/logs`). Only predefined, non-secret event codes, UTC time and optional internal server/library IDs are written; arbitrary exception messages and URLs are excluded. The viewer filters by severity, server, library and UTC date. Files rotate at approximately 1 MB with four retained backups. These selected events are not a complete application or error log; existing events before activation are not reconstructed. A logging failure must not stop scans or delivery.

Scan records created before the start-time correction may show the completion time as their start time; the original start cannot be reconstructed. New successful, partial and failed scans record their start before querying BookOrbit.

Existing server URLs cannot be changed in place because existing library and book IDs belong to that source; create a new server configuration for another instance. Rotating a stored webhook URL requires explicit confirmation because pending deliveries will use the replacement destination. A manual scan is available only with the opt-in runtime enabled; it does not itself trigger an unrelated delivery pass.

Server configuration supports an optional public base URL, a 1–120 second connection timeout and TLS certificate verification. The public URL is stored but is not yet used to create BookOrbit links. Certificate verification is enabled by default; disabling it prevents verification of the server's identity. Older API clients that omit these fields when editing a server leave their existing values unchanged.

For an explicitly selected discovered library, the optional sample check queries at most one book, requests its detail and checks for a cover using the stored source client. It reports only whether a sample, metadata and cover are available. It does not modify BookOrbit, send Discord messages or prove access to every book in the library. A missing cover is reported separately from a failed request.

The `{{series_tag}}` variable is empty when the book has no series. Each template has two editable formats: the numbered format (for example `Part {{series_index}} of {{series}}`) and the fallback when a series has no number (for example `{{series}}`). The editor can preview both cases and a book without a series. These formats accept literal text and only the `{{series}}` and `{{series_index}}` placeholders; they do not execute code. Existing templates keep their current fields and receive default formats during migration.

Per-library delivery modes can be changed in the library view. Changes apply to future scheduling decisions; queue entries already scheduled retain their existing due time. The delivery history is paginated in groups of 50, supports a status filter, and allows explicit retries, with separate confirmation required for a successful prior delivery.

The sender-avatar settings include the bundled Notifier logo at global, webhook and library level. The administrator preview loads its local copy, while Discord receives a public, commit-pinned GitHub raw-image URL in the per-message `avatar_url` parameter. Discord must be able to reach that host; this does not require public access to BookOrbit. Choosing the logo never modifies the stored Discord webhook. The hosted asset can become unavailable if the repository or host becomes inaccessible; custom and original webhook avatars remain available independently.

The arrivals view displays detected new-book events in pages of 50 as a list, table or cover grid and supports filters for server, library, author, genre, format, language, UTC detection date and delivery status. It does not show the initial silent baseline. A detail view displays selected metadata, metadata-check counts and timing, a failure indicator without the source error text, scheduled retry or in-progress delivery timing, and the most recent 200 delivery attempts; source file paths and credential fields are omitted. Displayed schedules are earliest times and actual processing can occur later. The optional cover button and lazily loaded grid covers fetch JPEG, PNG or WebP through the authenticated BookOrbit client and serve them only to the authenticated administrator; they never expose a source key or URL to the browser. Missing covers show a placeholder rather than blocking the rest of the view.

The webhook test button sends a fixed test message to the selected destination. The preview editor also provides an explicitly confirmed action to send the current sample preview and unsaved sender profile to the selected webhook. A selected library must be routed to that destination. Preview test messages are marked `TEST`; neither kind changes the Discord webhook or creates a normal arrival event.

An administrator-provided screenshot shows a real arrival with its cover displayed in Discord. Authenticated source cover retrieval and the source-to-Discord attachment flow have also been tested separately; the screenshot alone does not trace the individual HTTP requests. It shows Discord's default avatar, so it does not verify Discord fetching the bundled sender logo.

The Discord preview uses fixed sample metadata and the same safe renderer as delivery. Title, description, footer, color, cover inclusion and up to 25 ordered metadata fields can be saved as a named template and assigned to libraries; previewing alone neither saves nor sends a message. When enabled, the preview and its test message use the same bundled example cover, not a real BookOrbit cover. Actual notifications retrieve covers through the authenticated source client and attach them to Discord; if a cover cannot be fetched, delivery continues without one. Grouped notifications containing covers are delivered individually. The variable selector marks `book_url` and `cover_url` as unavailable until safe links are implemented; existing templates remain compatible. Each metadata field occupies its own Discord row. `duration` displays whole minutes as `HH:MM h`, or `MM min` below an hour; `duration_seconds` retains the source value. Empty metadata fields are omitted and content exceeding Discord embed limits is visibly truncated. Actual field availability depends on the BookOrbit version and each book's metadata. The sender name and custom avatar are resolved using the selected global, webhook and library settings, including unsaved edits. Original Discord values can be loaded explicitly using Discord's read-only [webhook endpoint](https://docs.discord.com/developers/resources/webhook); only the name and public avatar URL are returned to the browser, and the webhook itself is not modified. Original profile lookup and CDN avatar rendering have been tested with simulated Discord responses, not a live Discord instance. Custom and original avatar images load directly in the administrator's browser, so the image host can see its IP address; a successful browser preview does not prove Discord can reach a custom URL.
